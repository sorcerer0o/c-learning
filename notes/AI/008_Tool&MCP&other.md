# MCP / Agent / Tools概括

  # "为什么要有这些东西"

  用一句话开局：

  > 大模型本来只会"聊天"——你问一句，它答一句。要让 AI 能**查天气、搜网页、写文件、发邮件**，就需要给它装上"手脚"，这就是 Tool/Agent/MCP 这套体系的由来。

  

比如，你说接下来5天想去一个没有雨的地方，靠海边的地方玩5天，需要它帮我做一下行程规划。如果直接按照完形填空的方式，有可能找的地方正在下雨，不靠海边。所以，它需要查天气，查游玩的地方。确认位置之后，再安排具体的行程。 

比如，你问它你的 桌面下的某个文件夹中的C代码，有问题，为什么。

  ## 概念层级关系（最核心的框架图）

首先从宏观层面先看一下，所以**上来先给架构全景**：

  ```
  ┌──────────────────────────────────────────────────┐
  │  8. 应用层    OpenClaw / Claude Code / Codex      │  ← 具体产品
  ├──────────────────────────────────────────────────┤
  │  7. 安全层    权限控制 + 用户确认 + 限流             │  ← 护栏
  ├──────────────────────────────────────────────────┤
  │  6. 决策层    Agent（ReAct 循环：推理→行动→观察）    │  ← 自主决策
  ├──────────────────────────────────────────────────┤
  │  5. 行为层    System Prompt + Memory              │  ← "人设"和记忆
  ├──────────────────────────────────────────────────┤
  │  4. 知识层    RAG（检索外部知识库）                  │  ← 查资料/提供知识
  ├──────────────────────────────────────────────────┤
  │  3. 工具层    Tools（搜索/读写/执行等具体功能）       │  ← 执行动作
  ├──────────────────────────────────────────────────┤
  │  2. 协议层    MCP（统一工具调用标准）                │  ← 接口标准
  ├──────────────────────────────────────────────────┤
  │  1. 基础层    Function Calling（结构化输出）        │  ← 模型底层能力
  └──────────────────────────────────────────────────┘
  ```

  

  **三层简化版（课堂记忆用）**：



  ```
  Agent（大脑：做决策）→ Tools（手脚：执行）→ MCP（接口标准：统一调用方式）
  ```

  

  **记忆比喻**：MCP = USB-C 协议，Tools = 键盘/U盘/显示器，Agent = 用户（决定插哪个）。



  # 各层详解

  ## Function Calling

Function Calling 是一种让大语言模型（LLM）以结构化参数调用外部函数或 API 的机制，本质上是将自然语言转化为可执行的 JSON 指令，实现模型与外部系统的交互。

1.**工作流程：**

1. 开发者在请求中向模型描述可用函数（名称、参数、功能）
2. 模型理解用户意图后，返回包含函数名和参数值的 JSON 对象，而非自然语言回复
3. 外部系统执行该函数，将结果返回给模型继续处理

2.**关键特点：**

- 模型不执行代码，只生成调用指令
- 参数填充基于上下文语义理解完成
- 支持多轮对话中的上下文相关性

 3.**流程**：



  ```
  用户："北京天气怎么样？"
    ↓
  模型输出：{"name": "get_weather", "args": {"city": "北京"}}
  // 这就是需要找一个工具来完成这个任务。 这是由大模型判断出来的。  判断之后，大模型会给出 需要调用的工具 + 参数
    ↓
  外部系统执行 get_weather("北京") → 返回结果
    ↓
  模型把结果整理成自然语言回复
  ```

  

  🍕 例子：打电话订披萨

想象你是一家披萨店的**接线员**，你的工作流程是这样的：

### 没有 Function Calling 的 AI（只会聊天）

```
顾客："我要订一个榴莲披萨，送到我家"

AI："好的呢亲！榴莲披萨真的很好吃，您真有品味～
      请问您需要多大尺寸的呢？需要加双倍芝士吗？
      对了，您知道榴莲披萨的历史吗？它起源于……"
```



AI 一直在**聊天**，但它**下不了单**，因为它的世界里没有"订单系统"这个东西。它只能陪你聊到天荒地老。



### 有 Function Calling 的 AI（能干事）

同样一句话，这次 AI 内部是这样运作的：

```
顾客："我要订一个榴莲披萨，送到北京市朝阳区望京SOHO"

         ↓
    AI 大脑分析这句话
         ↓
  输出一个结构化"指令"：
  
  {
    "function": "create_order",
    "params": {
      "item": "榴莲披萨",
      "address": "北京市朝阳区望京SOHO",
      "size": "大份"         ← AI 从上下文推断的
    }
  }
         ↓
   披萨店的后台系统收到这个 JSON
         ↓
   厨房开始做披萨，骑手准备出发
         ↓
   系统返回：{"order_id": "8823", "eta": "30分钟"}
         ↓
   AI 把结果翻译成人话：
   "订单已生成，编号 8823，预计 30 分钟送达！🍕"
```





## 关键理解

用这个例子对照你文档里的流程图：

| 你的流程           | 对应披萨例子                                  |
| :----------------- | :-------------------------------------------- |
| 用户输入           | "我要订榴莲披萨"                              |
| 模型输出结构化参数 | `{"function":"create_order", "params":{...}}` |
| 外部系统执行       | 披萨店后台下单                                |
| 返回结果           | `{"order_id":"8823"}`                         |
| 模型整理成自然语言 | "订单已生成，预计30分钟送达"                  |

**Function Calling 的核心就是这一步**：AI 不执行代码，它只是把用户的自然语言**翻译成一个结构化的"调用指令"**（JSON），交给外部系统去真正执行。

  ## MCP（统一协议层）

MCP（Model Context Protocol）是一个标准化协议，让 AI 模型通过统一接口接入外部工具和数据源，解决 Function Calling 的碎片化集成问题。

MCP 可类比为**AI 世界的 USB-C 接口**。USB-C 统一了设备充电和数据传输的物理标准，MCP 则统一了 AI 模型调用外部工具的通信协议。无论工具是数据库、API、本地文件还是浏览器，都通过同一套协议对接。





在你理解 Function Calling 的基础上，MCP 解决的是下一个问题：Function Calling 让 AI 能"叫出"函数名和参数，但如果每家 AI 调用同一个工具的方式都不一样，工具开发者就要为 Claude 写一套适配、为 Gemini 写一套、为 GPT 再写一套——烦死了。MCP 就是定了一个**统一标准**，让所有 AI 用同一种方式调用所有工具。



1:**一个生活例子**

想象你出差住酒店：

2.**没有 MCP 的时代：**

```
你到酒店 → 床头柜上一堆遥控器
  ├── 电视遥控器（三星专用）
  ├── 空调遥控器（格力专用）
  ├── 窗帘遥控器（杜亚专用）
  └── 投影仪遥控器（极米专用）

你要开空调 → 在四个遥控器中找到格力那个 → 对准 → 按开机
你要关窗帘 → 换杜亚那个 → 对准 → 按关闭
```



3.**有 MCP 的时代：**

```
你到酒店 → 床头柜上一个面板，四个按钮：
  [开电视] [开空调] [关窗帘] [投影]

不管你用哪家 AI，都按同样的按钮，酒店后台自动处理品牌差异。
```



MCP 就是那个**统一面板**。工具开发者只需要按 MCP 标准暴露接口，所有支持 MCP 的 AI 都能直接调用，不需要重复适配。



```
Function Calling  →  AI 能"喊出"要调哪个函数（模型能力）
       ↓
MCP               →  规定"喊"的格式和方式（统一协议）
       ↓
Tools             →  真正干活的工具（搜索、读文件、发邮件）
```





> Function Calling 是"嘴巴"（说出要调什么），MCP 是"普通话"（大家用同一种语言说），Tools 是"手脚"（真正干活）。



  ## Tools（工具层）

Tools层是AI Agent的“手”——它将大模型的决策能力转化为对外部世界的实际操作，是Agent从“只会说”到“能做到”的关键桥梁。

比如：`web_search`（搜索）、`web_fetch`（抓取网页）、`file_read` / `file_write`（文件操作）、`code_execute`（代码执行）



<span style=color:red;background:yellow>**Tools是实际干活的。 Function Calling 是大语言模型打算调用一个函数，并且将其参数拼凑出来，但是还没动手，知识打算调用。 **</span>

比如，你让AI，读取一下你本地盘里面的某个文件，统计一下有多少字符。 



第一步，AI 理解你的需求，知道要"读取文件"和"统计字符数"，然后输出一个结构化的调用指令，比如：

json

```
{
  "function": "read_file",
  "parameters": {
    "path": "C:/用户/文档/报告.txt"
  }
}
```



第二步，外部系统（比如你的 IDE 插件、桌面应用或 MCP Server）收到这个 JSON 指令，真正去执行文件读取操作，把内容读出来。

第三步，AI 收到文件内容后，进行字符统计，然后告诉你结果。

AI 始终不直接执行，它只负责"翻译和解释"。执行权永远在你可控的外部系统手里。

  ## RAG（知识层）

RAG是给大模型外挂的“可检索知识库”——让模型在回答前先查询外部资料，用检索到的信息增强生成质量，解决模型知识过时或缺乏私域数据的问题。

RAG相比于Tools等，它检索的数据是我们提供的。大模型训练时候没有得到我们公司的数据。

  | 对比维度       | Tools                         | RAG                                   |
  | :------------- | :---------------------------- | :------------------------------------ |
  | **做什么**     | AI 主动调用工具去**执行动作** | AI 从外部知识库**检索信息**来增强回答 |
  | **举例**       | 查天气、发邮件、写文件        | 查公司文档、法规条文、产品手册        |
  | **一句话区分** | Tools 是"**干活**"            | RAG 是"**查资料**"                    |



问： 我们公司请假流程是什么？我们公司婚假能休几天？

RAG将你的自然语言问题转化为向量检索，在员工手册中匹配最相关的条款，然后将条款原文+问题组合成提示词让大模型生成精准回答——本质是“把正确答案先找出来，再让AI照着读”。



1.**步骤1：问题向量化（Embedding）**

- 输入：“我们公司请假流程是什么？我们公司婚假能休几天？”
- 系统调用embedding模型，将整句转化为一个高维向量（如768维）
- 这一步相当于把问题“压缩”成数学坐标

2.**步骤2：向量检索（Retrieval）**

- 查询向量数据库，内部存储着员工手册所有段落对应的向量
- 计算余弦相似度，找出最相关的top-K个段落（如K=3）
- 检索结果可能包含：
  - “请假需提前填写OA申请单，由直属上级审批”（相似度0.92）
  - “婚假：正式员工可享13天连续假期，需提供结婚证复印件”（相似度0.89）
  - “事假：每月累计不超过3天”（相似度0.45，不太相关被过滤）

3.**步骤3：上下文构建（Context Construction）**

- 系统将检索到的相关段落拼接成上下文块

- 组装最终提示词：

  ```
  请基于以下公司制度回答用户问题：
  [检索内容：请假需提前填写OA申请单...婚假13天...]
  用户问题：我们公司请假流程是什么？公司婚假能休几天？
  回答要求：仅基于提供的信息，不编造
  ```

4.**步骤4：生成回答（Generation）**

- 大模型读取提示词，输出精准回答
- 回答中会明确引用制度内容，如：“根据员工手册，请假需提前填写OA申请单...婚假为13个自然日...”

 

  ## System Prompt / Memory（行为层）

System Prompt是AI的“岗位说明书”和“行为准则”，Memory是AI的“工作笔记本”——前者定义AI的角色、能力边界和回答风格，后者记录跨对话的用户信息和历史上下文。



1.**System Prompt（系统提示词）**

- 在每次对话开始时注入，位于对话的最顶部
- 定义AI的“人设”：你是谁、能做什么、不能做什么
- 设定回答规则：格式偏好、语言风格、内容边界
- 类比：操作系统的环境变量 + 公司入职手册

2.**Memory（记忆机制）**

- 跨对话持久化存储用户信息、偏好和历史关键点
- 通过工具调用（memory_save/update/delete）主动管理
- 检索后动态注入到当前对话上下文中
- 类比：浏览器的Cookie + 本地数据库

分层协作流程

**完整调用链**（以你当前使用的系统为例）：

1. 系统启动时加载System Prompt（固定角色定义）
2. 用户发起新对话时，检索该用户的Memory记录
3. 将相关Memory注入System Prompt下方（形成完整上下文）
4. 用户每次输入都基于这个完整上下文进行推理
5. 对话过程中AI可主动调用memory_save更新记忆

  | 概念               | 作用                                                |
  | :----------------- | :-------------------------------------------------- |
  | **System Prompt**  | 设定 AI 的角色、行为准则、输出格式                  |
  | **Instructions**   | 告诉 AI"什么时候用什么工具"、"遇到什么情况怎么处理" |
  | **Memory（记忆）** | 跨对话保存用户偏好，让 AI 越用越懂你                |

  > 这三者是 Agent 行为的"**软件层**"，和 Tools 的"硬件层"形成对比。

 

  ## Agent（决策层）—— **ReAct 循环**

ReAct循环是AI Agent的“思考-行动-观察”决策框架——让大模型像人类解决问题一样，交替进行推理（Reasoning）和行动（Acting），通过多轮迭代完成复杂任务。

  Agent 是"自主决策的 AI"，但不知道它**具体怎么决策**。ReAct 是目前主流范式：

  ```
  Reason（推理）→ Act（行动）→ Observe（观察）→ 循环
  ```

  

<span style=color:red;background:yellow>**核心机制（三层循环）**</span>

**单次循环结构**（类比调试循环）：

1. **Reasoning（思考）**：模型分析当前状态，决定下一步做什么
2. **Acting（行动）**：执行一个具体操作（调用工具、查询知识、生成输出）
3. **Observation（观察）**：获取行动结果，更新对问题的认知
4. 重复以上三步，直到任务完成或达到终止条件

**工作流程示例**（用订披萨场景映射）：

text

```
用户：“帮我查一下北京明天的天气，然后推荐适合穿什么”

循环1：
- Thought：需要先获取天气数据，应该调用天气查询工具
- Action：web_search("北京 明天 天气")
- Observation：返回“明天北京 晴 22-28°C”

循环2：
- Thought：天气晴朗，适合轻便夏装，可以给出穿搭建议
- Action：生成最终回答
- Observation：任务完成，终止循环
```



<span style=color:red;background:yellow>**技术实现（工程视角）**</span>

**Prompt结构设计**（核心是让模型遵循这种格式）：

```
You are an AI assistant. You have access to these tools: [工具列表]
Use the following format:
Thought: 你对当前情况的分析
Action: 工具名称（参数）
Observation: 工具执行结果
...（重复直到完成）
Final Answer: 最终回复给用户的内容
```



**关键设计决策**：

- **循环终止条件**：模型输出Final Answer或达到最大迭代次数（如15次）
- **工具调用规范**：Action输出必须严格遵循可解析格式（如JSON），系统解析后执行
- **上下文管理**：每次循环的Thought、Action、Observation都追加到对话历史中，让模型“记住”之前的所有步骤

  

**实例演示**：

  | 步骤        | 内容                                                         |
  | :---------- | :----------------------------------------------------------- |
  | **Reason**  | 用户说"帮我整理今日 AI 新闻" → 我需要先搜索 → 再阅读 → 再总结 |
  | **Act**     | 调用 `web_search` 搜索新闻                                   |
  | **Observe** | 搜索结果返回 10 条链接                                       |
  | **Reason**  | 需要逐条阅读内容                                             |
  | **Act**     | 调用 `web_fetch` 读取链接                                    |
  | **Observe** | 内容读取完成                                                 |
  | …循环…      | 直到任务完成，生成简报                                       |

 

  ## 安全防护层

安全层是AI系统的“免疫系统”——在模型生成回答或执行操作前，对输入和输出进行风险检测、过滤和拦截，防止有害内容传播、敏感数据泄露或恶意指令执行。

给 AI 工具权限是有风险的。

  | 风险                     | 应对措施                |
  | :----------------------- | :---------------------- |
  | AI 被诱导删除文件        | 工具调用前需用户确认    |
  | AI 调用付费 API 产生费用 | 设置调用次数 / 金额上限 |
  | AI 访问敏感数据          | 权限控制 + 数据脱敏     |

  **记忆梗**：不要让 AI 有 `rm -rf /` 的权限。

一个行业标准术语：**Human-in-the-Loop（人类回圈/人工介入确认）**。

- **干活（只读）：** 查天气、搜网页、读文件 $\rightarrow$ Agent 自主执行。
- **危险（写/执行）：** 删文件、转账、发送邮件、执行危险脚本 $\rightarrow$ **必须弹窗让用户手动点【允许】**。

 

  ## 应用层（具体产品）

  | 产品            | 定位                                                 |
  | :-------------- | :--------------------------------------------------- |
  | **Codex**       | OpenAI 的代码生成模型，GitHub Copilot 的前身（2021） |
  | **OpenClaw**    | Anthropic 开源的 MCP 参考实现，用于概念验证          |
  | **Claude Code** | Claude 生态的编程辅助工具链，商业产品                |

Codex、OpenClaw、Claude Code 都是“Agentic Coding Assistant”——它们是专门为编程任务优化的 Agent，核心工作模式就是你描述的那个循环：理解需求 → 调用工具（读文件、搜索代码、运行测试）→ 观察结果 → 再决策 → 再调用，直到任务完成。

这三个产品的定位层次不同：Codex 是“发动机”（基础模型），OpenClaw 是“参考实现”（开源脚手架），Claude Code 是“量产车”（商业产品）。





```TEXT
用户输入 → 大模型理解意图 → 大模型输出 Function Call（JSON）
→ Agent 执行 Tools（读文件、搜索网页、运行命令）
→ 把结果返回给大模型 → 大模型判断是否完成
→ 如果没完成，继续输出新的 Function Call → 循环
→ 如果完成，输出最终答案给用户
```



初学者最容易产生一个幻觉：觉得大模型是一个“活着的灵魂”，它在自己脑子里转 ReAct 循环（思考 $\rightarrow$ 行动 $\rightarrow$ 观察）。

大模型本质上是一个“静态的函数”**。输入一段话，输出一段话，它自己**不会跑任何循环。 真正控制 ReAct 循环、去调用外部工具（Tools）、把工具结果拼回 Prompt 的，是**外层的代码系统（比如 Python/TypeScript 写的 Agent 框架）**。大模型只负责在每一次被“唤醒”时做选择题。





 1. Codex（OpenAI，2021）

**一句话定义**：Codex 是 OpenAI 基于 GPT 微调出的**代码生成专用模型**，GitHub Copilot 的内核引擎。

**核心能力**：

- 根据自然语言注释生成代码（“写一个快排函数” → 输出 Python 代码）
- 补全函数、类、测试用例
- 支持 Python、JavaScript、Go 等十几种语言

2. OpenClaw（Anthropic，开源）

**一句话定义**：Anthropic 开源的 **MCP 参考实现**，用于演示如何把 Claude 接入各种 Tools 并构建 Agent。

**核心能力**：

- 提供了标准的 MCP Client 实现，展示如何连接并管理多个 MCP Server。

- 内置了极简的 ReAct 决策循环，可以作为开发者自己动手写 Agent 的“毛坯房/脚手架”。

- 提供了开箱即用的命令行交互界面（CLI），方便开发者直观观察工具调用链。

3. Claude Code（Anthropic，商业产品）

**一句话定义**：Anthropic 推出的**商业级 AI 编程助手 Agent**，类似 GitHub Copilot 但基于 Claude 模型，支持更复杂的多步骤任务。

**核心能力**：

- 理解整个代码仓库（不只是当前文件）
- 执行多步骤任务：分析需求 → 搜索代码 → 修改文件 → 运行测试 → 修复错误 → 提交 PR
- 通过 MCP 协议调用各种 Tools（文件系统、Git、测试框架、Linter）

  ## 时间线（历史脉络）



  ```
  2021: Codex 发布（代码生成模型的起点）
  ```

  # 实战案例串联

  > **场景**：让 AI 帮我整理一份"今日 AI 新闻简报"

  | 阶段              | 发生了什么                                                   |
  | :---------------- | :----------------------------------------------------------- |
  | **1. 用户输入**   | "帮我整理今日 AI 新闻简报"                                   |
  | **2. Agent 推理** | 理解目标 → 拆解为"搜索 → 阅读 → 总结 → 写文件"               |
  | **3. MCP 调用**   | 通过统一协议调用工具，不关心每个工具的内部实现               |
  | **4. Tools 执行** | `web_search`（搜索新闻）→ `web_fetch`（抓取文章）→ `artifact_create`（生成简报文件） |
  | **5. 输出**       | 一份完整的新闻简报文件                                       |

  ## 易混淆概念辨析

  | 易混淆                  | 正确理解                                                |
  | :---------------------- | :------------------------------------------------------ |
  | MCP vs Tools            | MCP 是**协议**，Tools 是**具体功能**                    |
  | Agent vs Tools          | Agent 是**决策者**，Tools 是**执行者**                  |
  | Claude Code vs Codex    | Codex 是**模型**，Claude Code 是**工具链产品**          |
  | OpenClaw vs Claude Code | OpenClaw 是**开源参考实现**，Claude Code 是**商业产品** |
  | Tools vs RAG            | Tools 是"干活"，RAG 是"查资料"                          |
